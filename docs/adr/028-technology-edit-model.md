# ADR 028 — Technology edit model

- **Status**: Accepted
- **Date**: 2026-08-12

_The TL edit form is not a new form. The descriptor-driven technology ML form already exists and
already writes (`technology-form-descriptor.ts` → `api.entity.write`), with the ADR-022 `@NAME`
overwrite warning intact. The editable canvas needs exactly two things the current form lacks: it is
opened from a selected canvas node instead of a file view, and it must edit the technology `.txt` and
its localisation `.yml` **atomically** — a rename touches both files, and a half-committed rename
orphans or destroys a loc key. This records the edit model: reuse the form, add a public-name
(localisation) field, and swap the single-file `api.entity.write` for the ADR-027 cross-file batch.
The reason to write it down before the edit ticket is that the same model is shared by **add** and
**delete** — three tickets build on it — and the pivot that decides loc cleanup (autogenerated vs
custom token) is subtle enough that re-deriving it three times would get it wrong at least once. It is
additive to ADR 018, 021, 022, 024, 026, and 027 and amends none of them. The two shape-sensitive
rules it depends on — the autogen normalization rule and the loc-key derivation — are **deliberately
not asserted here**; they are read from BICE at implementation (ledger `L-023`)._

## Context

The pieces the TL edit form composes already exist and are verified against the code:

- **The form is descriptor-driven and complete for script fields.** `technology-form-descriptor.ts`
  (`libs/r-game-hoi4/src/technology/`) projects a `TechnologyEntity` into an `EntityFormModel` (ADR 018)
  built from `propertyBag` (the root scalars), `objectList` (`path`, `folder`) — the `folder` block
  carrying a nested `position` object — and `listOfScalars` (the ref-lists: `dependencies`, `xor`,
  `categories`, `enable_equipments`, …) blocks. It exposes `research_cost` and `start_year`
  (`TECHNOLOGY_ROOT_SPECS`), `leads_to_tech` (`TECHNOLOGY_PATH_SPECS`), and `folder.position`'s `x`/`y`
  (`TECHNOLOGY_POSITION_SPECS`). This is a working, tested surface, not a sketch.
- **It already writes — single-file.** `save` computes scoped deltas (`computeTechnologyDeltas`) and calls
  `api.entity.write({ deltas, entityName: token, modId, relativePath })` — one `relativePath`, the ADR-019
  single-file write path. That is precisely the assumption the TL surface breaks (ADR 027): a rename edits
  the technology `.txt` **and** a localisation `.yml`, two files that must land together.
- **The ADR-022 `@NAME` warning is intact and must stay intact.** `confirmBeforeSave` calls
  `collectSymbolReplacements`, which names every `@NAME`-bound field the save would overwrite with a
  literal (ADR 022 decision 6). This behavior is not touched by this model — it inspects script-field
  deltas, and the loc field is not a script field.
- **The cross-file batch exists.** ZMT-47/48 delivered `write-batch.service.ts` (ADR 027) with two format
  strategies — `ast-scoped-delta.strategy.ts` (Clausewitz `.txt`) and `loc-lines.strategy.ts` (localisation
  `.yml`, `LocDelta` = set / insert / delete). A batch is a set of `{ absolutePath, format, delta }`
  operations applied all-or-nothing. This is the write target the form swaps to.

Two facts sharpen the model:

- **The current form edits script fields only.** The localised display name lives in a loc key in a `.yml`,
  which the form does not read or write today. `doctrine_name` is a *script* field, not the loc key — the
  form has no localisation field at all. Adding one is the substantive change, not a cosmetic one: it is the
  first field on this form whose write lands in a different file and a different format.
- **The technology token and the public name are two different strings that can move together or not.** The
  token is the technology's file id / block name; the public name is the localised string a loc key holds.
  Whether renaming the public name moves the token — and therefore whether the old loc key goes stale —
  depends on how the token was chosen (decision 4). This is the whole reason loc cleanup is not uniform.

## Decision

### 1. Reuse the existing form; open it from the canvas; route its write through the batch (Q84)

The TL edit form **is** the existing `technology-form-descriptor` + ML form shell (ADR 018), opened from a
**selected canvas node** (ADR 026's selection is the precondition) rather than from a file view. Its write
is swapped from the single-file `api.entity.write` to the **ADR-027 batch service**, so the technology
`.txt` edit (an `ast` operation) and the localisation `.yml` edit (a `loc` operation) commit as **one atomic
batch** — either both land or neither does, with the residual-window semantics ADR 027 decision 3 states
once and every batch consumer inherits.

**Rejected: a purpose-built TL form.** It discards a working, tested descriptor and its delta machinery to
rebuild the same script-field editing behind a canvas, and it would re-open the `@NAME`-overwrite question
ADR 022 already closed. The delta cost of the TL surface is one new field plus a write-target swap; a new
form pays far more for nothing the existing one lacks.

### 2. `start_year` and placement stay independent (Q85)

The descriptor already carries `start_year` (a root scalar — the technology's actual in-game research year)
and `folder.position` (the placement grid cell) as **separate fields**. They remain independent: editing
`start_year` never moves the node, and moving the node never changes `start_year`. The form must not couple
them.

On **Add**, the new technology's `start_year` **default** is seeded from the clicked row's gutter-year (via
the ADR-025 geometry year-axis), but it is **immediately, independently editable** — the seed is a default,
not a binding. This is the single point where the two quantities touch, and it touches only at creation, only
as an initial value.

This is a direct application of ADR 025's three-distinct-quantities rule, which ADR 026 already enforced for
the read-only canvas: `start_year` (research year), `position.y` (a layout row / cell index), and the gutter
year (what the `.gui` prints at a row) are **three distinct quantities**. The edit form conflating any two —
most temptingly, snapping `start_year` to the row a node is dragged to — is the exact defect ADR 025 was
written to prevent. Record that it must not.

### 3. Public name is a localisation field, written in the same batch (Q86)

The TL form adds a **public-name field** that reads and writes the technology's display-name loc key via the
**loc-lines strategy** (ADR 027 decision 2), in the **same batch** as the technology write. A rename that
touches both the technology file and the `.yml` is therefore atomic — it lands together or rolls back
together (decision 1). This is the first form field whose write is a `loc` operation rather than an `ast`
one; the batch is what lets a single Save span the two formats without a partial write.

The script-field half of the form is unchanged: the existing `propertyBag` / `objectList` / `listOfScalars`
blocks, their deltas (`computeTechnologyDeltas`), and the `@NAME` warning (`collectSymbolReplacements`) all
behave exactly as today. The public-name field is **added alongside** them; it does not alter script-field
behavior.

### 4. The token is custom or autogenerated; that state drives loc cleanup (Q86)

The technology token (its file id / block name) is in one of two states, and the state — **not** the fact of
a rename — decides whether stale loc cleanup fires:

- **Autogenerated** — the token is derived from the public name by a normalization rule (this is the default,
  and it is also what a **cleared** token field falls back to). Because the token is a function of the public
  name, changing the public name **regenerates the token**, so the old autogenerated loc key no longer
  corresponds to any technology: it is stale. The batch **deletes the stale key and inserts the new one** —
  both as `loc` operations in the same atomic batch as the technology write.
- **Custom** — the token is user-entered and **stable**. It does **not** change when the public name changes.
  A rename is then a loc **`set`** on the existing key; there is **no stale cleanup**, because the token — and
  therefore the key — did not move. Custom tokens are the user's to own; treating one as autogenerated would
  destroy a key the user deliberately named.

State the pivot precisely: **stale-key cleanup fires only for autogenerated tokens, because only they move.**
Getting it wrong in either direction is a data defect — autogen-not-cleaned **orphans** loc keys; custom-treated-
as-autogen **destroys** user-owned keys (Consequences).

### 5. This model is shared by add and delete

Edit is the first consumer, but the model is deliberately the **shared** one:

- **Add** opens this same form (at the click position; the safe-position calculation is the add ticket's
  concern) and commits via the **same batch** — the technology insert (an `ast` insert delta, ADR 027 decision
  4, closing L-012) and its loc-key insert (a `loc` insert) as one atomic operation.
- **Delete** reuses the **loc-cleanup logic** of decision 4 — removing a technology removes its loc keys — with
  the same autogen-vs-custom pivot governing which keys are removed.

Recording the model here, once, keeps add and delete **consistent with edit** rather than re-deriving the
loc-batch coupling and the autogen pivot three separate times. Each of the three lands on its own ticket
(R-WORK-14); this ADR is the shared substrate, not any one of them.

### 6. The loc-file target is a later `resolveWriteTarget` concern

**Which** `.yml` file a loc key is written to is a toolbar / preferences setting — a later ticket, and the same
`resolveWriteTarget` seam ADR 027 already recorded as out of scope (its decision-5 routing targets the editable
*owner*, not a user's save-target preference). This model routes to a **default / passed-in loc target** for
now and records the **seam** so it is wired as a parameter, not hardcoded forever. The batch service already
takes its write config as parameters (ADR 027 decision 6, Electron-free by design); the loc target rides the
same parameterization.

## Grounding deferred to implementation (do NOT specify here)

Two rules this model depends on are **shape-sensitive** and are read from real BICE technology + localisation
pairs at implementation, **not asserted in this ADR**. Recent tickets (ADR 022 / 024 / 025 / 026) repeatedly
found the real on-disk shape differs from a recalled one; the discipline is read-shapes-don't-recall, and it
applies here too. Recorded as ledger `L-023`:

- **The autogen normalization rule** — how a public name becomes a token (case handling, separators,
  punctuation stripping), and **collision handling** when two names normalize to the same token. Record only
  that the rule is grounded from BICE convention at implementation and that collisions **must** be handled;
  do not assert the rule.
- **The loc-key derivation** — which loc keys a technology needs (the name key; a `_desc` / description key?;
  anything else) and how each is derived from the token. Record that this is grounded at implementation.

Asserting either here would bake a recalled shape into an accepted decision — the precise failure mode the
last four ADRs each paid to avoid.

## Consequences

**Positive**

- **Edit, add, and delete share one model**, defined once. The write is always a **batch** (atomic
  technology + loc), so a rename can never leave the `.txt` and the `.yml` disagreeing.
- **The working form is preserved.** The existing ML form's script-field writes and the ADR-022 `@NAME`
  warning are unchanged; the TL form **adds** the loc field and **swaps** the write target. No script-field
  behavior is re-implemented or re-risked.
- **The autogen-vs-custom pivot is stated once**, so add and delete inherit it rather than re-deriving the
  loc-cleanup rule — the same "state it once, every consumer inherits it" discipline ADR 027 applied to the
  batch's residual window.

**Negative / accepted**

- **The autogen-vs-custom pivot is load-bearing and easy to get wrong.** It is the pivot for loc cleanup, and
  a mistake in either direction is a data defect: an autogenerated token not cleaned on rename **orphans** the
  old loc key; a custom token mistakenly treated as autogenerated **destroys** a key the user owns. This ADR
  fixes the rule; the implementation must apply it exactly.
- **The loc-file target is deferred to `resolveWriteTarget`.** Until that ticket lands, a **default** loc
  target is used. This is an accepted, recorded seam (decision 6), not an oversight — the alternative,
  hardcoding a target now, is the thing the seam exists to prevent.
- **Two shape-sensitive rules are named but not specified** (the autogen normalization rule and the loc-key
  derivation, ledger `L-023`). The model carries the cost of naming what it does not yet know rather than
  guessing it — the same deferral ADR 025 (`L-021`) and ADR 026 (`L-022`) each made.

**Deliberately out of scope, recorded so the omission does not read as oversight**

- Any change outside `docs/`. Reading the code and BICE to verify is expected; editing is not. The loc field,
  the write-target swap, and the batch wiring land on the edit ticket.
- The **safe-position calculation** (add), the **cascade model** (delete), the **context menu**, the
  **toolbar / `resolveWriteTarget`**, and the **hover card** — each its own ticket.
- The **autogen normalization rule** and the **loc-key derivation** themselves — grounded at implementation
  (`L-023`), not here.

## Alternatives considered

- **A purpose-built TL form** instead of reusing the descriptor. Rejected — it discards a working, tested form
  and its delta machinery, re-opens the closed `@NAME`-overwrite question (ADR 022), and pays a large cost for
  a delta that is one field plus a write-target swap (decision 1).
- **Couple `start_year` to node placement** (e.g. snap the research year to the dragged row). Rejected —
  `start_year`, `position.y`, and the gutter year are three distinct quantities (ADR 025); coupling them is the
  exact defect ADR 025 exists to prevent, and ADR 026 already refused it for the read-only canvas
  (decision 2).
- **Write the technology `.txt` and the loc `.yml` as two separate single-file writes.** Rejected — that
  reintroduces across two files the partial-write hazard ADR 019 removed within one: a rename that updates the
  script file but fails on the `.yml` leaves the technology renamed and its display name stale, with no
  rollback. The atomic batch (decision 1) is the whole reason the write target is swapped.
- **Clean up loc keys uniformly on every rename** (or never). Rejected — cleanup is correct **only** for
  autogenerated tokens, which move with the public name; a custom token does not move, so cleaning its key
  destroys a user-owned key, and *not* cleaning an autogenerated key orphans a stale one. The autogen-vs-custom
  pivot (decision 4) is the rule; a uniform policy is wrong in one of the two states either way.
- **Assert the autogen normalization rule and the loc-key derivation in this ADR.** Rejected — both are on-disk
  shapes read from BICE at implementation, not recalled (ledger `L-023`), the same discipline ADR 022 / 024 /
  025 / 026 each turned on.
